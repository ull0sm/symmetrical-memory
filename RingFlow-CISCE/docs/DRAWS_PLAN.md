# Draws Overhaul — Plan

Branch: `feat/draws-overhaul`. Status: **planning, no code changed yet.** Written 2026-10-02.

## 1. Intent (why draws exist in RingFlow)
A draw is the tournament's contract: who fights whom, in what order, and how medals are decided.
It must be **fair** (random or seeded, reproducible), **defensible** (audit trail, checksum, no
silent changes once fighting starts), **usable on a messy floor** (odd sizes, unattached athletes,
last-minute withdrawals) and **printable** (paper sheets still run most venues). It must work
offline.

Two tournament modes (decided by the user):
- **Official** — strict WKF procedure: direct elimination with repechage, two bronzes, optional
  ranking seeds, electronic draw.
- **Local / Unofficial rules** — WKF rules as a base, tweaked for local constraints (1 bronze bout, joint bronze,
  no bronze; organiser-chosen seeding; looser separation).

## 2. Research summary (sources)
- WKF: kumite is direct elimination with repechage; the draw is electronic, made after the
  technical meeting; seeding may apply by world ranking.
  [WKF 2026 Kumite Rules](https://www.wkf.net/files/pdf/documents/WKF_2026_Kumite_Competition_Rules_MASTER_COPY_V12.pdf),
  [Karate Technical Regulations](https://fagames2026.fisuamerica.com/wp-content/uploads/2026/06/Karate-Technical-Regulations-EN-V2.pdf)
- WKF kata: two pools; elimination round, ranking round, then gold bout (pool winners) and two bronze
  bouts (A#2 v B#3, B#2 v A#3). [WKF: What is kata](https://www.wkf.net/news-center-new/olympic-games-karate-competition-what-is-kata/1632)
- Tournament software norms: seeding first, then academy/club separation so same-club athletes meet as
  late as possible; byes go to top seeds; the draw method is recorded.
  [MartialMatch seeding](https://martialmatch.com/en/help-center/how-does-bracket-seeding-work)
- Not verified: I could not read the WKF "Competition System" PDF (binary); exact seed counts per
  event size should be confirmed against it before hard-coding "official" seed positions.

## 4. Design
**Draw profile** (`OFFICIAL` | `LOCAL`) stored on the tournament, overridable per category, recorded
on each draw. It controls defaults only: bronze format, separation strictness, whether manual
overrides are permitted. Engine stays pure; profile is an input.

**One draw model.** Kumite brackets and kata pools both produce a `DrawGraph` (`format` = elimination
or kata pools), with a seed, a checksum over the full stored body, rounds/matches/slots and pools.
`match_slots` gets the `repechageRule` (or is derived on read from the graph — see Q3).

**Reproducibility.** Draw seed is chosen once, stored in `draws`, shown to the admin, and written to the
audit log. Regenerating with the same seed and roster yields the same draw. All randomness goes through
the seeded PRNG (no `Math.random` anywhere in draw code).

**Seeding & separation.** Optional seeds (import column + UI) occupy standard seed positions; the rest are
random. Separation groups by club (unattached athletes each their own group). Separation tries several
seeds/swaps to minimise clashes before warning; seeded athletes are not moved unless needed.

**Safety.** Server refuses regeneration when any bout is LIVE/CONFIRMED (no force flag). Flush is the only
destructive path: typed confirmation + reason, audited, admin only. Lock check and delete live in one
transaction. Bronze/profile changes mark the draw "stale" until regenerated.

**PDF.** Split generator into layout (pure, testable geometry), primitives, and per-format sheets.
Fix text encoding (embed a Unicode font, e.g. Noto Sans, bundled offline; fallback strips marks safely).
Watermark DRAFT; separate "draw sheet" (no results, printable before the event) from the results
state sheet. Kata gets a real pool-sheet layout with pagination. Stop calling subtrees "pools".

## 8. Phase 8: split a category's pools across tatamis (2026-10-02, user request)
**Why:** a 64-athlete category prints as four pools of 16. With two tatamis the admin gives pools 1-2 to tatami 1 and 3-4 to tatami 2, so a pool winner is not left waiting for 48+ other bouts before meeting the other pool winners. Same for kata pool flights (Pool A / Pool B). Official and local events both do this.

**Decisions (user):** cross-pool bouts (semi-finals, finals, bronze, repechage) run on ONE tatami the admin picks when splitting, and wait until every pool feeding them has finished; a pool takes its normal slot in its tatami's queue; kumite and kata ship together; the UI says "Pool" (the PDF's "Section" wording is reverted).

**Today:** `category_assignments` has `unique(category_id)`, so a category lives on exactly one tatami; `scopeForMatch` finds a bout's tatami through that one row; completion (`bouts/results.ts`, `kata/finalize.ts`), stager, attendance, public, judge and the dashboard all assume one assignment per category.

**Design:** keep the assignment as the unit of "one tatami runs it", but allow several per category, one per *part*.
- `matches.part` (text, null = whole category): `POOL:1..N` for the bouts of a 16-slot pool (kumite first-round + the 3 later rounds of that subtree; kata pool bouts of Pool A/B), `FINALS` for everything after (semis/final, bronze, repechage; kata Final Flight). Set when the draw is stored, from the graph, so it is part of the checksummed draw and reproducible.
- `category_assignments.part` (text, default `ALL`); unique becomes `(category_id, part)`. An unsplit category keeps one `ALL` row and behaves exactly as today.
- `scopeForMatch` joins on `(category_id, part = coalesce(match.part, 'ALL'))` so the existing guards (`requireMatchModerator`) authorise on the right tatami without change elsewhere.
- Split action `splitCategoryAcrossRings(categoryId, {pools: {1: ringA, 2: ringA, 3: ringB, 4: ringB}, finalsRing})` (admin only, audited, broadcast): refused once any bout is fought or the category is running; creates the part assignments in each tatami's queue; `unsplit` merges back (same refusal). Needs a draw first (parts come from the draw).
- Start rule: a `FINALS` part cannot start until every `POOL` part is `completed` (server-checked in the start action; the queue shows "waiting for pools 3-4").
- Completion: a part is complete when all its bouts are done; the category is complete when all parts are. Podium/results logic only when the last part completes.
- Screens: balancing page gets a "Split pools" dialog on a category; queue/dashboard/public/stager show "Category X · Pools 1-2" and "Category X · Finals"; draw-sheet PDF prints the assigned tatami on each pool page.
- Migration 16 (idempotent): add columns, backfill `ALL`, swap the unique constraint, add status check for `part` shape.

**Done (2026-10-02, branch `feat/split-pools-across-tatamis`):** all phases below shipped together. Migration 16 adds `matches.part` and `category_assignments.part`; pure `computeDrawParts` labels bouts (kumite pools = the 16-place subtrees under round 3; kata Pool A/B); `performSplitCategory` / `performUnsplitCategory` (+ audited `splitCategoryPools` / `unsplitCategoryPools`) with a split dialog on the balancing board; scoring authority, the desk view, result counting and kata advancement follow a bout's part; the finals card waits for the pools; `saveAssignments` keeps a split category's pool cards in place (pure `sequenceQueue`); regenerate refuses a split category, flush collapses it; draw sheets print each pool's tatami and say "Pool" not "Section". Verified by `scripts/verify-pool-split.ts`, `tests/http/test-pool-split.mjs` and unit tests. **Not done:** dragging individual pool cards between tatamis on the board (unsplit and re-split instead), a "waiting for pools" hint on the finals card (the server refuses with a clear message), the stager call area shows a split category once, at its finals tatami.
